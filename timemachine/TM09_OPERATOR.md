# TM09 operator handoff (ledger 222, queue 115)

This is build machinery, not authority to launch, fetch market data, score, or inspect results. The service must use a dedicated non-root account (proposed `tm09desk`) and private `/var/lib/tm09` (0700). Use a root-owned, read-only, pinned TM09 release in a separate directory, for example under `/opt/tm09-releases/`, plus dedicated TM09-only worker scratch and briefs. Do not use TM07 paths, tape, service user, ports or credentials. Schedule setup separately from the live TM07 sessions. Proposed configurable launch pool: 8801–8806, subject to owner/operator allowlist and a fresh availability check. The server binds loopback only. Every `serve` takes its port explicitly.

## Prepare and sign

1. Place the recorded `stock_sessions.jsonl`, `stock_bars.jsonl` and `stock_news.jsonl` in the registered `tm09_stock_export` directory. Use ordinary non-symlink files, private to custody and the service, not the worker. Minute bars: `symbol,tf,t,o,h,l,c,v`, `tf=1Min`; `t` is the UTC minute-open epoch second. Use the full 38-name roster, regular-session minutes, exact venue close minute, and sufficient preceding recorded session-calendar coverage to avoid attributing an older item to the first study wake. News clocks and metadata follow `tools/tm09_stock_news_counts.py`; do not run that script for author review. `stock_universe.jsonl` is supporting custody evidence, not input for dropping names. Export direct files or fail; never follow the TM07 tape symlink. Share export hashes and row counts only.
2. Provision a private 0600 signing-key file inside `/var/lib/tm09`; use a service-only random value of at least 32 characters. Never put it in argv, stdout, a prompt or repo. Custodian creates canonical signed capsules via `tm09_desk.seal(key, domain, body)` as `{"body": body, "seal": signature}` only after the lead authorizes that specific scope. A signature authenticates the custodian's attestation; it does not attest to provider behavior automatically. Store approvals and evidence privately. Use absolute direct paths, a pinned release, and invoke modules from that release as the dedicated service, not as the worker or root.
3. Each capsule body binds `root`, `service_uid`, absolute `release`, `approved_by`, `release_files` (SHA-256 map for the modules, tests and brief listed in `tm09_operator.approved`), `config_sha256`, and `registration_sha256`. Build scope `ledger-222-build-fixtures` also binds `export_sha256`, a map keyed by exactly the three input basenames. Run `python3 -m timemachine.tm09_operator build --root ROOT --key-file KEY --approval BUILD_CAPSULE`. Output is one private no-headline fixture per week, plus canonical fixture digests in `fixture-pins.json`. Do not print data or the fixtures.
4. Rehearsal scope `ledger-222-rehearse-tm09` binds the same release, `resolved_settings` (exact output of `tm09_fixture.settings` before adding limits), `limits` (`notes`, `note_chars`, `looks`, `look_rows`, `headline_rows`, `headline_chars`), an operator's `operator_boundary_sha256` attestation and explicit `ports`. Pass `--rehearsal` to `create`, `serve`, and `export-notes`. It uses the built-in invented case for the week `2026-09-07`, in a separate subdirectory; no live feed reader is constructed or used. Run the actual provisioned news scout on the invented fixture and verify the first and second wake packet outcomes and the absence of the note in P1/P2. Record a count-and-digest-only proof. The Python unit test uses a scripted paraphrase and is not proof that the hosted model or deployment environment passed.
5. Run scope `ledger-222-run-tm09` additionally binds `export_sha256`, `fixture_pins`, and `synthetic_rehearsal_sha256`. Sign only after review of the rehearsal, no-web/no-outside-tool enforcement, private-feed delivery, provider no-training/no-raw-logging controls and the operator's worker boundary evidence. Input beyond signed bounds is refused rather than silently truncated. Confirm that the signed ports are a subset of the agreed pool.

## Create, serve and review

Use `python3 -m timemachine.tm09_operator COMMAND --root ROOT --key-file KEY --approval CAPSULE --week YYYY-MM-DD --role ROLE`. For a boss add `--boss MODEL --arm P1|P2|N`. For `serve` only, add `--port PORT`. Confirm the exact ready line before briefing: `Registered desk ready; brief only this session's roles.` Give the worker only its own bearer, SID and endpoint plus the pinned brief and, for a successor, verified same-session handoff. End every worker before reuse of its sandbox, bearer transport, or port. The service signs notes once, after scout completion. `export-notes` saves only the immutable wake-indexed notes to `scout-export.json`; `create` the two scouts first, then all six bosses. Price-side workers must not be able to traverse or open any service files. The service reads the pinned headline export at the news scout endpoint only; do not turn on transport or model request/response dumps.

If a worker is lost, stop it and run `successor` once on the same slot. Provide the replacement bearer and the signed same-session handoff; old bearer and wake key no longer work. Keep completed session state intact. Never restart a completed worker or create a replacement slot to repeat its run. A refusal, dependency failure or missing bar is not evidence of a completed outcome.

Before production, run `python3 -m timemachine.tm09_isolation_probe` from the actual sandboxed worker against an active invented rehearsal desk and again with `--stopped` after service stop. Use `--port`, `--session`, `--sibling`, `--bearer-file`, and repeated `--canary` with direct paths to existing TM09-only harmless stand-ins for private tape, notes, key and results. The canaries must exist and deny reads, not merely be absent. Separately verify network egress restrictions and approve the role-to-route and shell allowlists. Capture the operator's before/after no-sudo audit boundary and compare only allowlisted operator activity; do not ask a worker or build process to run sudo. Review redacted command/endpoint receipts and the TM09 journal for scope, role, stop, and successor checks. These are deployment controls; the loopback server is not an OS sandbox, proxy, or review of hosting policies.

The runner stores decisions, accepted-note text, fill and completion receipts. It does not store raw news payloads. The news-note filter rejects a complete current or previously seen headline even if case and punctuation change; it cannot prove that all notes are sound paraphrases. Require isolated operator/provider controls and a privacy review policy before real feed delivery, without exporting quotations or using the other arms' prompt context.

## Close and score

Profit figures are not worker routes. At window close and only on separate lead approval, use scope `ledger-222-seal-results` with `window_closed: true` and the same run evidence, then run the operator `results` command without week/role/arm arguments. It writes private `sealed-results.json` with every scheduled week, completion/null statuses, and delivery counts; stdout contains no return. Keep analyst access closed until the score ceremony.

Run `python3 -m timemachine.score_tm09 --root ROOT --approval SCORE_CAPSULE --key-file KEY --registration REG --config CONFIG --sealed-results SEALED` only with lead approval. Score capsule domain `tm09-score-approval`; body fields `scope: ledger-222-score-once`, `root`, `approved_by`, `config_sha256`, `registration_sha256`, `results_path`, `results_sha256`. It refuses before opening the result path unless approved. The exclusive score claim remains on any failure; stop and reconcile with the lead, do not delete the claim to retry. Keep `scored.json` private and arrange the independent blind recomputation from the same seal before reporting.

## Rulings and limitations

TM04 allowed fractional positions; the later TM09 registration supersedes that for bosses. Only the benchmark is fractional. The order request is a long-only whole-share target vector sized from completed marks; costs sit inside the available cash and capped remainder is canceled. Missing prior sizing marks or missing exact terminal marks cause refusal, not synthetic price substitution. An active order whose first later minute does not fall strictly before the next decision wake or session close also causes refusal: confirm with the lead how to handle multi-wake/overnight stale orders or incomplete venue data rather than inventing carry or cancellation semantics. The stored wording's original historical vintage and Alpaca hosted-model clearance remain the registration's open questions.
