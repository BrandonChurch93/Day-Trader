## First deliverable: timestamp-only source decision

- **Bitstamp first:** Use the [documented public OHLC endpoint](https://www.bitstamp.net/api/) keyless for the approved USD spot pair identities. The API page permits making “new original works, statistics” from its exchange data and directs commercial users to its data-license contact. Work within its stated request limits and recheck them before collection: the page gives 400 requests per second, a default 10,000 per ten minutes, and at most 1,000 candles per OHLC request. Use the supported one-hour step, bounded chronological windows and completed candles only. The documentation says the end parameter wins if both date bounds are sent; do not depend on sending both to enforce a date range. Filter the returned stamps against the intended window. STATED clock convention: the bar stamp is its UTC opening time. Confirm this from the API documentation, not from prices; do not continue with an unresolved clock.
- **Coverage receipt:** Deliver private `coverage_receipt.json` before any price decode. The top-level fields are `checked_utc`, `venues`, `selected_venue` (null if neither passes), and `outcome` (source selected or closed on coverage). The ordered `venues` list includes Bitstamp and only if it falls short, Kraken. Each venue record has `venue`, `documentation_url`, `query_windows` (UTC bounds and completion status), `coins` and `qualifying_coin_count`. The `coins` list has one row per roster name: `coin`, `usd_pair` (null for a proved absent product), `first_bar_utc`, `last_bar_utc` (null if none), `hourly_stamps_by_utc_year` (distinct aligned stamps in each probe year), `gaps_over_six_hours` (bounding UTC stamps, elapsed hours and number of missing slots), and `covered` (boolean). Use first/last source stamps evidenced by the probe and its boundary checks, including stamps on or outside the two-year fence to test both ends; record clock bounds and do not claim a lifetime first or last without evidence. Include gaps intersecting the two-year window. A missing response or ambiguous product is not evidence of absent coverage; complete or refuse the receipt before applying the fallback. No price field is opened, parsed, logged, saved or forwarded in this stage. Project only pair identity and timestamp tokens; discard every price field.
- **Fixed order:** The timestamp test is distinct from the doc 172 full-trading mask. Only a completed Bitstamp receipt below the floor permits checking the [official Kraken downloadable hourly USD files](https://support.kraken.com/articles/360047124832-downloadable-historical-ohlcvt-open-high-low-close-volume-trades-data) by the same criteria. The [Kraken Global Terms](https://www.kraken.com/legal/global-terms) have broad automation restrictions; the ledger records the lead agent's reading of the conflicting official download instructions. Use only the approved private workflow and only summary results in the repo. No Kraken API price call, mix of venues, or later switch after seeing prices.

> A coin counts as covered on a venue when, by time stamps only, its first hourly bar is on or before 2022-01-01 00:00 UTC, its bars run past 2023-12-31 23:00 UTC, it has at least 95% of the 8,760 hourly stamps in each of 2022 and 2023, and no gap is longer than 72 hours in those two years. Gaps over 6 hours are listed in the receipt. Bitstamp is the source if 10 or more of the 20 coins are covered; otherwise Kraken's files, judged the same way; if neither venue covers 10, the plan closes on coverage with no price read. Only covered coins are eligible. A missing hour is never filled in: a fall is measured only between two adjacent hourly closes that both exist, and a trade whose exit bar is missing is void and counted.

## Fixed handoff

- **Folders:** `/home/user/workspace/rig/data/plan_76/{count,design,heldback}`, with each stage folder owner-only mode 0700 and its inputs regular single-link mode-0600 files owned by the runner. Symlinks are rejected. No production collection, stage start or score is part of this build.
- **Bars:** `bars.f64` is headerless little-endian IEEE binary64, hour-major from start inclusive to stop exclusive, then the full alphabetic roster from config. Each count cell holds just close; design and held-back cells hold open then close. Missing bars are NaNs (both fields together in scored tapes). Opens and closes use the same hourly bucket, labeled by its opening UTC hour; a signal first becomes usable when the bucket has closed. Bitstamp's named OHLC object fields and Kraken's documented row fields are normalized by the custodian using the approved clock; `read_bars` consumes the same canonical tape with no native-layout or venue branch. The tape never carries venue flags or data from outside the fence. The runner applies doc 172 trading windows from config, not from the source.
- **Manifest:** `manifest.json` is UTF-8 JSON with exactly `schema` (integer per config), `stage` (count, design or heldback), `start` and `stop_exclusive` (UTC dates), `source_release` (opaque release ID using ASCII letters, digits, periods, hyphens or underscores and starting with a letter or digit), `source_release_end_exclusive` (UTC date), `names` (all roster names alphabetically), `covered_names` (alphabetical list of distinct covered names from the selected venue's timestamp receipt), `hours` (integer number of UTC slots), `bars_sha256`, `source_receipt_sha256`, `coverage_receipt_sha256` and `prior_result_sha256`. Hashes are lowercase full SHA-256. The covered names and coverage-receipt hash must remain identical across stages. In held-back the fence end must equal the named release end; in count and design the release end must cover the whole design fence. Prior result is null for count; design pins the preceding count result bytes, and held-back pins the preceding design result bytes. The config's tape and metadata length limits are technical fuses, not a permission or a different date fence.
- **Receipts:** `source_receipt.json` records the above rights decision, source/coverage details, byte hashes, pair mappings, gaps, and collection/extraction method. The scorer checks the exact receipt bytes against the manifest; it does not independently determine permission. `receipt.json` is UTF-8 JSON with exactly the schema integer, stage, `manifest_sha256`, and boolean `separate_custodian` and `permission_confirmed`, each true. A real custodian and lead review, not the booleans, establish that separation and permission.
