## Reruns and how they are counted

- A rerun after an engine fault is counted as a trial. Rerun R1 adds 36 and rerun R2 adds 8. R1 followed faults in the engine. R2 did not: the engine was right and rule I2 was coded differently from its pushed plan. The owner's exception names the engine only, so R2 may not be covered by it. That is questions 18a and 18b in `archive/decisions/morning_list_2026-11-25.md`. R1 itself also carried two changes that were not engine faults: amendment rows A13 (a stricter pass mark 1) and A08 (what holding pays when the break-even cost is worked out). Row A12 is an engine fix to the 0.10 band check that changes the trades of one rule, P2. Research recommends that no pass from R1, from R2 or from the first run of replay 05 is credited, and that every number is kept as a measurement. The owner has not answered. R2 is counted as trials either way. R2 counts all 8 rules, not only the one that changed, because all 8 were run again on the held-back slice and pass mark 4 is worked out across the set.
- Neither rerun was counted when it ran. Each run used the count that was in this ledger when its plan was frozen: 20 for the daily rules in replay 01 and in rerun R1, 36 for the hourly rules, 44 for replay 05 in both of its runs, 49 for replay 04. Under the owner's rule those counts are too low for rerun R1 and for everything after it.
- What that does to the results, MEASURED by `ledger_count_check.py` from the stored outputs, written to `ledger_count_check.json`. The script runs no rule and reads no prices. It works out pass mark 3 again for every stored row with every trial and rerun to date counted (the `count_all` value in that file). A larger count can only lower a deflated Sharpe, so it can turn a pass into a fail and never the other way.
- The answer is in that file under `passes_that_become_fails` and `mark3_passes_that_become_fails`, and in `docs/STATUS.md`: the row "Trial count check" in the results table holds the figures, and "Known faults and slips" holds the account of the slip. No number from it is typed here.
- From now on a rerun gets its row in the same commit as its amendment, before it runs, and the run uses the count that includes it.
- The check above is a sum on stored outputs. It is not a rerun, changes no stored result and adds no trial.
- One more run to disclose. `i2_2020_note.py` reads one held-back year of the industry file and describes it. It was run once more on 2026-11-25 after its data path line changed (commit c7956c4). The output was identical to the stored file. It runs no rule, has no pass mark and is not counted. So it was not strictly unchanged code. Whether a repeat like that is allowed at all is question 16a in the morning list, and what to do about this one is 16b.
- More repeats to disclose, found by a cold-read test on 2026-11-25. `export_dashboard.py`, which makes the data for the owner's screen, replayed five runs that were already in the stored results, of three rules (P1 on bitcoin at two costs and on ether, and hourly rules H1 and H7 on bitcoin; this line said "five rules" until 2026-11-25 13:15 UTC, which was loose wording) over the whole price history, held-back years included, each time it was run, to draw their curves and list their trades. It was run several times on 2026-11-25 and the number of times was not recorded. Each time it compared four whole-sample figures with `results_v2.json`, for the rule and for holding (growth a year, Sharpe ratio, largest drop, total return), to within one part in a billion, and the trade count for the three daily charts, and would have stopped on a difference. It changed no stored output and no rule or setting. It did produce new material: the curves, the year-by-year figures and the trade lists shown on the owner's screen. No stored output holds those, nothing checks them, and the saved curves are not in the repo. An earlier version of this line said it "produced no new number", which was wrong. These repeats are not counted as trials. They are a second run of the held-back slice for the same version of a rule, which the owner's rule says never to do, and research did not see that at the time. Since 2026-11-25 the script reads saved curves and replays nothing unless it is given `--resimulate`. This is question 16b.
- `pilot/server.py` served price history to the AI models in pilot 02 and read Bitstamp prices up to 2026-11-24. It ran once, for the pilot. It is on the list of scripts that read held-back prices.
- `provenance.json` records, for each stored output, the command, the commits and the input fingerprints. It was built after the runs, not by them.
